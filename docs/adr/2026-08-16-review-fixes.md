# ADR 2026-08-16 — 코드 리뷰 지적 반영: 실패를 감추지 않는 방향으로 동작 변경

- **Status**: Accepted — 2026-08-16 (실기 재구동 검증 예정 — 검증 결과는 `docs/code_updates/2026-08-16-review-fixes.md`)

## Context

[2026-08-15 리뷰](../code_review/dss_ros2_bridge/2026-08-15.md) 와 [2026-08-16 delta](../code_review/dss_ros2_bridge/2026-08-16.md) 가 지적한 항목 중 **공개 표면·관측 가능한 동작이 바뀌는 것**만 본 ADR 이 다룬다. 순수 내부 수정(`snprintf` 교체, 캐스팅 타입 정정, dead code 삭제, 빌드 의존성 선언)은 동작이 같으므로 ADR 대상이 아니다.

지적들의 공통점은 **실패가 조용하다**는 것이다. 세 갈래로 나타난다.

1. **NATS 연결 실패** — 생성자가 `std::cerr` 한 줄 뒤 `return` 하고 정상 종료한다. `rclcpp::spin` 은 그대로 돌아 퍼블리셔·타이머·구독이 하나도 없는 노드가 영원히 산다. `ros2 node list` 에 정상 등재되고 종료 코드도 0 이라, 감시 측·launch 측 어디에서도 실패를 알 수 없다. (리뷰 High #5)
2. **`DSSVssClient::start()` 무시** — 싱글톤 생성자가 이미 기본 인자(`ip="172.25.96.1"`)로 연결해버려서, 이후 `start("100.80.80.15", …)` 은 `conn != nullptr` 검사에 걸려 `NATS_ERR` 만 반환한다. 호출부는 반환값을 보지 않는다. 결과적으로 **호출자가 지정한 주소가 조용히 무시된다.** 실측상 `172.25.96.1:4222` 는 이 환경에서 도달 불가(timeout)이고 브리지 노드들이 쓰는 `100.80.80.15:4222` 만 살아 있어, 데모 노드만 다른(죽은) 서버를 향한다. (리뷰 High #4)
3. **비정규화 쿼터니언 통과** — DSS 가 보내는 `orientation` 의 노름이 실측 **0.707131** 인데 브리지가 그대로 발행한다. TF2·robot_localization 은 단위 쿼터니언을 전제하므로 소비자 쪽에서 자세가 틀어지거나 거부된다. 브리지는 아무 신호도 내지 않는다. (delta 리뷰 신규 High)

추가로 **토픽 이름 불일치**가 있다 — `DSSToROSPointCloudNode` 는 `/dss/sensor/lidar3d` 를 발행하는데 `DSSDemoNode` 는 `/dss/sensor/lidar` 를 구독한다. 발행자가 없어 데모의 포인트클라우드 콜백은 한 번도 실행되지 않는다. (리뷰 Medium #1)

## Decision

### 1. NATS 연결 실패는 생성자에서 예외로 올리고, `main` 이 잡아 비정상 종료한다

```
생성자: 연결 실패 → RCLCPP_FATAL → throw std::runtime_error
main:   try { spin(make_shared<Node>()) } catch (...) { RCLCPP_FATAL; return 1; }
```

재시도 루프는 넣지 않는다. 프로세스 감독(`ros2 launch` 의 `respawn`, systemd, 컨테이너 재시작 정책)이 이미 그 일을 하며, 노드 안에 재시도를 넣으면 감독자가 실패를 볼 수 없어 같은 문제가 한 겹 안으로 숨을 뿐이다.

### 2. `DSSVssClient` 생성자는 연결하지 않는다 — 연결은 `start()` 만 수행한다

싱글톤 획득(`singleton()`)과 연결 개시(`start()`)를 분리한다. 호출자가 준 주소·포트가 실제로 쓰인다. `start()` 는 이미 연결된 상태에서 다시 불리면 종전대로 `NATS_ERR` 을 반환하되, **호출부가 반환값을 검사**하도록 고친다.

### 3. `createImu` 는 쿼터니언 노름을 검사한다

- 노름이 0 에 가까우면(`< 1e-6`) 단위 쿼터니언으로 대체
- 노름이 1 에서 `1e-3` 이상 벗어나면 **경고 로그(throttle) 후 정규화**해서 발행

정규화만 하고 침묵하지 않는 이유: 원천이 성분을 빠뜨리는 종류의 결함이면 정규화된 값도 여전히 틀린 자세다. 로그가 있어야 원천 조사로 이어진다. 반대로 로그만 하고 비정규화 값을 그대로 내보내면 소비자가 매 프레임 깨진다.

### 4. `DSSDemoNode` 의 라이다 구독 토픽을 `/dss/sensor/lidar3d` 로 맞춘다

발행 측 이름을 바꾸면 패키지 밖 소비자가 끊긴다. 구독 측을 발행 측에 맞추는 방향이 영향이 작다.

## Alternatives

- **연결 실패 시 재시도 타이머** — 기각. 위 1 의 근거(감독자가 실패를 못 봄). 필요하면 launch 의 `respawn=true` 로 선언적으로 붙인다.
- **연결 실패 시 현행 유지(조용한 무동작)** — 기각. 리뷰 High #5 그 자체.
- **`start()` 가 재연결(기존 연결 끊고 새 주소로)** — 기각. 싱글톤을 공유하는 다른 사용자의 연결을 끊는 부작용이 생긴다. 분리가 더 단순하고 안전하다.
- **쿼터니언을 정규화하지 않고 그대로 발행 + 경고만** — 기각. 소비자가 쓸 수 없는 값이 계속 나간다.
- **쿼터니언 이상 시 프레임 폐기** — 기각. 현재 DSS 가 **항상** 0.707 을 보내므로 IMU 토픽이 통째로 비게 된다.
- **발행 토픽을 `/dss/sensor/lidar` 로 되돌리기** — 기각. 패키지 밖 소비자에게 영향.

## Consequences

### 이득

- NATS 가 없거나 주소가 틀리면 **프로세스가 죽는다** — launch·감독자·CI 가 즉시 알 수 있다. 종료 코드 1.
- 데모 노드가 지정한 서버 주소로 실제 연결된다.
- `/dss/sensor/imu` 의 orientation 이 단위 쿼터니언이 되어 TF2·로컬라이저가 쓸 수 있다. 원천 이상은 로그로 계속 노출된다.
- 데모의 라이다 구독이 실제로 데이터를 받는다.

### 비용 / 남는 위험

- **동작 파괴 가능**: 지금까지 "NATS 없이도 노드는 뜬다" 에 의존하던 절차·테스트가 있으면 깨진다. 실측상 그런 사용은 없었다(연결 실패 노드는 아무 일도 하지 않았다).
- `launch.py` 는 `respawn` 을 선언하지 않으므로, NATS 가 늦게 뜨는 환경에서는 **노드가 죽은 채로 남는다.** 기동 순서 의존이 절차서에 이미 있다(리뷰 A-8 1단계 → 4단계). 필요하면 `respawn=True` 추가를 후속으로.
- **쿼터니언 정규화는 원천 결함을 고치지 않는다.** 노름 0.707 은 성분 누락 가능성이 크고, 그 경우 정규화 결과도 틀린 자세다. DSS 측 확인이 남는다 — delta 리뷰 신규 High 는 `[잔존]`.
- 싱글톤 생성자가 연결하지 않으므로, `start()` 를 부르지 않고 `get`/`set`/`setDriveControl` 을 쓰던 코드는 이제 조용히 실패한다(`conn == nullptr` / `udp_socket_ < 0` 경로). 현재 호출부는 `DSSDemo.cpp` 하나이고 `start()` 를 부른다.

## Rollback

가역이다. `git revert <커밋>` 또는 항목별로:

1. 생성자의 `throw` 를 `return` 으로, `main` 의 `try/catch` 제거
2. `DSSVssClient` 생성자에 `start();` 복원
3. `createImu` 의 노름 검사 블록 제거
4. `DSSDemo.cpp` 구독 토픽을 `/dss/sensor/lidar` 로 환원

영속 상태·스키마·펌웨어를 건드리지 않는다.
