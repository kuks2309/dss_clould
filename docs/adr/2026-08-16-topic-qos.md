# ADR 2026-08-16 — dss_ros2_bridge 토픽 QoS 를 메시지 크기 기준으로 분리 지정

- **Status**: Accepted — 2026-08-16 (실기 검증 완료: NATS 100.80.80.15:4222 + DSS 시뮬레이터 가동 상태에서 before/after 계수 측정)

## Context

9개 브리지 노드와 데모 노드는 pub/sub 을 전부 **정수 depth 인자**(`create_publisher<T>(topic, 10)`)로 만들었다. rclcpp 에서 이 형태는 `rmw_qos_profile_default` 를 쓰므로 실제 프로파일은 KeepLast(10) · **RELIABLE** · Volatile 이다(근거: `/opt/ros/humble/include/rmw/rmw/qos_profiles.h:51-62`).

착수 시 가설은 "922 KB 이미지를 RELIABLE 로 보내면 유실·지연이 생기니 센서 스트림 전체를 `SensorDataQoS` 로 바꾼다" 였다. **실측이 이 가설을 두 번 뒤집었다.**

### 측정 1 — 변경 전 RELIABLE 은 이미 무손실이었다

NATS 원천 발행 수와 ROS2 수신 수를 같은 20초 창에서 계수 대조했다.

| 토픽 | 메시지 크기 | NATS 원천 | ROS2 수신 | 유실률 |
| --- | --- | --- | --- | --- |
| `/dss/sensor/camera/rgb` | 921,600 B | 121 | 122 | ~0 % (창 경계 오차) |
| `/dss/sensor/lidar3d` | 148,478 B | 121 | 121 | 0.0 % |
| `/dss/sensor/imu` | 수백 B | 2433 | 2428 | 0.2 % |
| `/clock` | 수십 B | 2433 | 2428 | 0.2 % |

초기에 `ros2 topic hz` 가 5.2 Hz 를 보고해 유실로 오인했으나 짧은 관측창의 아티팩트였다. **성능 근거는 성립하지 않는다.**

### 측정 2 — 전면 `SensorDataQoS` 전환은 대용량 토픽에서 회귀를 만들었다

전 센서 토픽을 `SensorDataQoS`(BEST_EFFORT) 로 바꾼 뒤 토픽별로 분리 측정했다.

| 토픽 | 메시지 크기 | BEST_EFFORT 유실률 |
| --- | --- | --- |
| `/dss/sensor/camera/rgb` | **921,600 B** | **37.8 %** |
| `/dss/sensor/lidar3d` | 148,478 B | 0.0 % |
| `/dss/sensor/imu` | 수백 B | 0 % (-0.1) |

경계는 **메시지 크기**에 있다. 비압축 `rgb8` 프레임은 RTPS 조각화(fragmentation) 전송을 타는데, best-effort 는 재전송이 없어 **조각 1개 손실이 샘플 전체 손실**이 된다. 148 KB 인 포인트클라우드에서는 나타나지 않았다.

### `/clock` 은 프로파일이 실제로 어긋나 있었다

발행자(본 패키지)는 `RELIABLE` 인데 구독자 9개(rviz2·transform_listener 등)가 전부 `BEST_EFFORT` 였다. rclcpp `TimeSource` 의 기본 `/clock` 구독 QoS 가 `rclcpp::ClockQoS()`(KeepLast(1) · BEST_EFFORT) 이기 때문이다(근거: `time_source.hpp:64`, `qos.hpp:339-357`). RxO 상 통신은 되지만 **어떤 구독자도 요구하지 않은 신뢰성**을 120 Hz 토픽에 얹고 있었다.

관련 리뷰 항목: `docs/code_review/dss_ros2_bridge/2026-08-15.md` Medium `[QoS]` — 그 항목의 "지연·큐 적체" 서술은 측정 1 로 정정된다.

## Decision

**단일 프로파일을 강요하지 않고, 메시지 크기·용도에 따라 나눈다.**

| 대상 | 프로파일 | 근거 |
| --- | --- | --- |
| 이미지 5종 (`camera/rgb`, stereo color·depth·infra1·infra2) | `rclcpp::QoS(rclcpp::KeepLast(10)).reliable()` | 922 KB 조각화 전송. best-effort 시 실측 37.8 % 유실 |
| `/dss/sensor/imu`, `/dss/sensor/gps/fix`, `/dss/sensor/lidar3d` | `rclcpp::SensorDataQoS()` | 무손실 확인 + ROS2 센서 스트림 관례 |
| `/clock` | `rclcpp::ClockQoS()` | rclcpp `TimeSource` 기본 구독 프로파일과 정확히 일치 |
| `DSSDemoNode` 구독 3개 | 짝이 되는 발행 프로파일과 동일 (이미지만 reliable) | RxO 호환 유지 |

정수 depth 대신 **QoS 클래스·명시 빌더**를 쓴다. `10` 이라는 숫자만 남으면 reliable 이 의도인지 기본값 방치인지 구별되지 않는다.

## Alternatives

- **전 센서 토픽 `SensorDataQoS`(관례 일괄 적용)** — **기각**. 관례에는 맞지만 이미지 토픽에서 실측 37.8 % 유실. 관례보다 측정을 따른다.
- **현행 유지(전부 정수 `10` = RELIABLE)** — 기각. `/clock` 의 불필요한 신뢰성 비용이 남고, 의도가 코드에 드러나지 않는다.
- **이미지를 `sensor_msgs/CompressedImage` 로 발행** — **보류(권장 후속)**. DSS 는 이미 JPEG(83 KB)를 보내는데 브리지가 이를 922 KB 로 디코드해 발행한다. 압축 그대로 넘기면 11배 작아져 best-effort 로도 무손실이 되고 대역도 준다. 다만 소비자가 받는 데이터 형식이 바뀌는 **기능 변경**이라 QoS 범위 밖이다.
- **OS 소켓 버퍼·RMW 튜닝으로 조각 손실 완화** — 기각(범위 밖). 패키지가 아니라 배포 환경 설정이며, 환경마다 재적용해야 한다.

## Consequences

### 이득

- 이미지 유실률이 37.8 % → **0.0 %** 로 복구(측정 3, 아래).
- `/clock` 이 rclcpp `TimeSource` 기본값과 같은 프로파일이 되어 요구되지 않은 신뢰성 비용이 사라진다.
- imu·gps·lidar 는 ROS2 센서 관례(`SensorDataQoS`)를 따르면서 무손실을 유지한다.
- QoS 의도가 코드에 명시된다(정수 리터럴 → 프로파일 클래스).

### 비용 / 남는 위험

- **공개 인터페이스 변경 — 호환성 파괴가 실증되었다.** best-effort 발행자는 reliable 구독자와 연결되지 않는다(RxO: offered < requested). 변경 후 reliable 구독자로 측정하니 **4개 토픽 모두 수신 0 건**이었고 rclcpp 가 경고를 냈다:
  `New publisher discovered on topic '/clock', offering incompatible QoS. No messages will be received from it. Last incompatible policy: RELIABILITY`
  → `imu`·`gps/fix`·`lidar3d`·`/clock` 을 reliable 로 구독하던 외부 소비자는 **조용히 끊긴다**. `SensorDataQoS`(또는 rclpy `qos_profile_sensor_data`)로 맞춰야 한다. RViz2 는 해당 디스플레이의 Reliability 를 `Best Effort` 로 바꿔야 한다.
  → 이미지 토픽은 reliable 유지이므로 기존 소비자 영향 없음.
- **토픽마다 프로파일이 다르다** — 일관성이 떨어져 보이지만 근거가 측정이며 코드 주석에 이유를 남겼다. 이미지가 `CompressedImage` 로 바뀌면 이 예외는 사라지고 전부 `SensorDataQoS` 로 수렴할 수 있다.
- `/clock` 을 depth 1 로 구독하면 계수상 15~16 % 가 "유실" 로 보인다. clock 은 절대 시각이라 최신 1개만 유효하고 rclcpp `TimeSource` 자체가 depth 1 이므로 기능상 문제는 아니다(유효 122 Hz). 이 수치를 성능 지표로 오독하지 않도록 명시한다.
- QoS 를 파라미터로 노출하지 않았다 — 환경별 조정이 필요하면 `qos_overrides` 활용을 후속으로 둔다.

### 측정 3 — 변경 후 확인

| 토픽 | 최종 프로파일 | 원천 | 수신 | 유실률 |
| --- | --- | --- | --- | --- |
| `/dss/sensor/camera/rgb` | RELIABLE · KeepLast(10) | 145 | 145 | **0.0 %** |
| `/dss/sensor/lidar3d` | BEST_EFFORT · KeepLast(5) | 144 | 145 | 0 % |
| `/dss/sensor/imu` | BEST_EFFORT · KeepLast(5) | 2902 | 2909 | 0 % |
| `/clock` | BEST_EFFORT · KeepLast(1) | 2903 | 2447 | 15.7 % (depth 1 특성, 유효 122.3 Hz) |

## Rollback

가역이다.

1. 각 `create_publisher`/`create_subscription` 의 QoS 인자를 정수 `10` 으로 환원(= 변경 전 `rmw_qos_profile_default`).
2. `colcon build --symlink-install` 후 재기동.
3. RViz2 설정의 Reliability 를 `Reliable` 로 되돌린다.

영속 상태·스키마·펌웨어를 건드리지 않으므로 데이터 마이그레이션은 없다.
